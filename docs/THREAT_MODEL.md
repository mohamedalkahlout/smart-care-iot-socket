# نموذج التهديدات وتحليل الأمان المعماري (THREAT_MODEL.md)
**المنهجية:** نموذج مايكروسوفت STRIDE  
**النطاق:** نظام المقبس الذكي (ESP32 Firmware + REST/MQTT API + لوحة التحكم)

---

## 1. مخطط تدفق البيانات (Data Flow Diagram - DFD)

```
[مستخدم محلي (زر)] ──GPIO4──► [ESP32 Core] ◄──GPIO15── [حساس DHT22]
                                   │
                                   ▼
                            [حارس الأمان C++]
                                   │
                                   ▼
                              [الريليه GPIO2] ──► [الجهاز الكهربائي]
                                   ▲
                                   │ (HTTPS/TLS)
                                   ▼
                       [Firebase RTDB / Cloud]
                                   ▲
                                   │ (OAuth / Session Token)
                                   ▼
                     [لوحة الويب / تطبيق مقدم الرعاية]
```

## 2. مصفوفة تحليل التهديدات (STRIDE Threat Matrix)

| فئة STRIDE | التهديد المحتمل | ناقل الهجوم (Attack Vector) | التأثير | إجراء التخفيف المعتمد (Mitigation) |
|---|---|---|---|---|
| **S** - انتحال الشخصية (Spoofing) | انتحال هوية المقبس أو مقدم الرعاية | إرسال أوامر PUT مباشرة إلى رابط REST المكشوف | تشغيل غير مصرح به للأجهزة | اعتماد مصادقة Firebase Auth برموز جهاز مميزة (Device Token) ورفض أي طلب بدون توقيع صالح. |
| **T** - التلاعب بالبيانات (Tampering) | حقن قيم حرارة متطرفة أو أوامر خبيثة | تعديل حقول `minTemp`, `maxTemp`, أو `mode` بقيم غير منطقية (مثل `minTemp: -999`) | تعطيل منطق التحكم أو إجبار المقبس على العمل المستمر | قواعد أمان صارمة في `database.rules.json` تفرض قيود الأنواع والمدى (0°م إلى 45°م). فوق ذلك، حارس الأمان الداخلي يرفض أي أمر يتجاوز الحدود الفيزيائية. |
| **R** - التنصل (Repudiation) | إنكار تشغيل السخان أو تغيير الإعدادات | غياب سجل التدقيق التاريخي | عدم القدرة على تحديد المتسبب في الحادث | بناء سجل تدقيق مشفر (`audit_log`) يسجل معرف المستخدم، الطابع الزمني (NTP)، والعملية المنفذة بدقة. |
| **I** - كشف المعلومات (Information Disclosure) | استنتاج تواجد الأشخاص أو دورات نومهم | التنصت على تذبذب الأحمال والحرارة | انتهاك خصوصية الأطفال وكبار السن | تشفير كامل للاتصال عبر TLS 1.3، عدم تخزين بيانات سلوكية شخصية، وحصر التليمترية في الحالة التشغيلية للجهاز فقط. |
| **D** - حجب الخدمة (Denial of Service) | إغراق المقبس بطلبات سريعة أو قطع الإنترنت | هجوم Flooding أو تشويش شبكة Wi-Fi | عزل المقبس عن التحكم البعيد | المقبس مصمم وفق مبدأ **Offline-First**: انقطاع الشبكة يبقيه على آخر إعداد آمن مع مراقبة الحساس محليًا والاعتماد على الزر الفيزيائي. |
| **E** - تصعيد الصلاحيات (Elevation of Privilege) | تعديل مقدم الرعاية لحدود الأمان العليا | استغلال واجهة المستخدم لتجاوز قيود المالك | تعريض البيت لمخاطر حرارية | نموذج صلاحيات ثلاثي الطبقات (`owner`, `caregiver`, `viewer`)؛ حدود الأمان القصوى (`SafetyConfig`) مشفرة داخل الـ Firmware ولا يمكن تغييرها سحابيًا. |

## 3. قواعد التحقق الدفاعي في العمق (Defense-in-Depth)

1. **الطبقة الأولى (العتاد والـ Firmware):** حارس الأمان C++ مستقل تمامًا ولا يسمح بأي مسار يتجاوزه مهما كان مصدر الأمر.
2. **الطبقة الثانية (السحابة):** قواعد قاعدة البيانات ترفض الحقول غير المسموحة والقيم الشاذة.
3. **الطبقة الثالثة (التطبيق):** واجهة مقيدة بالأدوار وتأكيد ثنائي للأوامر الحرارية عن بعد.
